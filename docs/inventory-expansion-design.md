## 1. 목표와 관련 문서

기존 입점 판매자의 상품·재고·주문 모델을 유지하면서 플랫폼이 직접 매입한 상품을 공식 판매자 명의로 판매한다. 입점 상품과 직매입 상품을 한 주문·한 결제로 구매할 수 있도록 하고, 직매입에는 별도 재고 서비스와 창고·로트별 입출고 관리를 도입한다.

사용자는 재고 서비스 API를 이용하는 **B 경로**, 품절 품목을 제외하는 **② 상품별 부분 성공**, 아래 초기 운영 범위와 로컬 전체 플로우 검증을 승인했다. 이 문서는 그 합의를 구현 가능한 기준으로 정리한다. API 이름·상태 enum·물리 테이블명은 해당 단계에서 기존 코드와 대조해 확정한다.

- 개발 순서와 완료 조건: [단계별 계획](../.workflow/INVENTORY_EXPANSION_PLAN.md)
- 지속할 판단: [설계 결정 D-011~D-019](../.workflow/DECISIONS.md)
- 기존 보완 이력: [기존 1~6단계 계획](../.workflow/COMMERCE_REMEDIATION_PLAN.md)
- 결제 테스트 경계: [웹훅 계약](payment-webhook-contract.md)

기존 EC-CORRECTNESS-RESTART-20261007의 1~6단계는 completed다. 새 설계는 그 완료 판정을 다시 열지 않는다. 이번 문서 작성은 설계 저장이며 서비스 생성·코드 변경·DB 초기화·빌드·시나리오 실행이 아니다.

## 3. 판매 주체와 서비스 책임

고객 화면은 입점 상품에 판매자의 스토어명/이름, 직매입 상품에 프로젝트 공식 판매자명을 표시한다. 내부 분기는 변경 가능한 표시 이름을 비교하지 않고 서버가 관리하는 고유 판매 주체 ID와 유형을 사용한다. 일반 판매자가 공식 판매자로 등록하거나 자기 상품의 유형을 플랫폼으로 바꿀 수 없어야 한다.

주문에는 판매 주체·판매 방식·재고 경로·상품명·단가·요청 수량·배송비 배분을 고정해서 기록한다. 이후 상품 정보가 바뀌어도 기존 주문·취소·환불·정산은 이 기록을 사용한다. 플랫폼 공식 판매자를 기존 판매자별 주문 묶음에 표현할 수 있지만, 이를 일반 판매자 정산이나 단일 배송 제약에 그대로 적용하지 않는다.

| 영역 | 책임과 경계 |
|---|---|
| product-service | 상품·가격·판매 주체·SKU 연결. 입점 재고는 기존 정책 유지. 직매입 판매 가능 수량의 최종 기준은 inventory-service다. |
| order-service | 입점 Redis 경로와 직매입 예약 API를 조율. 요청 상태·최종 주문 구성·사용자 확인·복구 진행을 기록한다. |
| 기존 판매자 재고 | InventoryReservationService의 Redis 예약·확정·해제·복원 및 관련 Product DB 동기화 흐름을 유지한다. |
| 신규 inventory-service | 별도 PostgreSQL DB에서 직매입 창고·SKU·로트·잔량·예약·할당·입출고·이동·실사·원장을 소유한다. 기본 WMS 업무를 내부 모듈로 구분하며 별도 WMS 서비스를 먼저 늘리지 않는다. |
| payment-service | 고정된 최종 주문 금액의 결제·환불. 판매 방식별 환불 대상을 구분하되 한 결제의 환불 한도·중복 방어를 유지한다. |
| shipping-service | 입점 배송 정책 유지. 직매입은 창고의 실제 출고 확정 이후 배송을 시작하며 출고 지시별 배송을 관리한다. |
| settlement-service | 입점 판매대금·수수료 정산을 유지. 플랫폼 직매입 판매·환불을 일반 판매자 정산 생성·차감 대상에서 제외한다. |

직매입 상품은 기존 PRODUCT_REGISTERED/PRODUCT_STOCK_UPDATED 소비자의 Redis 초기화·증감 및 InventoryStockReconciliationScheduler의 입점 재고 보정에서 구분한다. 상품의 조회용 수량을 제공하더라도 창고 잔량과 독립된 판매 승인 기준으로 사용하지 않는다. 공통 이벤트 계약을 바꾸면 기존 caller·consumer도 함께 검증한다.

## 4. B 경로와 ② 부분 성공 주문

### 예약과 최종 확인

1. 주문 서비스가 주문 시도·요청 내용·품목별 예약 ID를 먼저 영속화한다. 같은 주문 멱등 키에는 같은 처리 시도와 예약 ID를 사용한다.
2. 입점 품목은 기존 경로, 직매입 품목은 재고 서비스 API로 예약한다. DB 행 잠금·트랜잭션을 유지한 채 원격 API 응답을 기다리지 않는다.
3. 품절 등 업무 실패가 확정된 품목은 실패 사유와 함께 제외한다. 요청 수량 전체를 확보해야 품목 성공이다. 공급 주체나 수량을 임의로 대체하지 않는다.
4. 성공한 품목·예약 유효시간·최종 금액·배송비를 제공하고 사용자가 이 구성에 확인한 뒤 결제를 시작한다. 모두 실패하면 결제를 만들거나 진행하지 않는다.
5. 주문 구성/금액이 바뀌거나 예약이 만료되면 이전 확인으로 결제하지 않고 재확인한다. 서버가 보관한 주문 버전·금액을 검증하며 클라이언트가 보낸 판매 유형·가격을 신뢰하지 않는다.

실패 품목을 제외한 뒤 상품 금액·배송비·적용 중인 할인 배분을 다시 계산한다. 할인 기능이 없는 현재 상태에서 신규 쿠폰 시스템을 추가하지는 않는다. 직매입 배송비는 주문당 한 번 배분하고 취소 시 같은 비용을 두 번 환불하지 않도록 원본 배분을 보존한다. 무료배송 기준 미달로 취소 후 금액을 추가 청구하는 기능은 초기 범위에서 제외한다.

### 응답 유실과 해제 복구

- 타임아웃·연결 오류는 품절이 아니다. 예약 성공 여부 미확인 상태에서는 최종 결제 가능 주문으로 응답하지 않는다.
- 같은 예약 ID로 상태 조회·재시도를 수행하고, 동일 ID의 다른 대상·수량은 충돌로 거부한다.
- 제한된 확인 후에도 결과를 모르면 기술 오류/처리 중 상태와 주문 조회 경로를 제공한다. 중단·사용자 취소·만료된 시도의 해제 진행을 영속화해 재시작 후 복구한다.
- 해제가 예약 생성보다 먼저 도착하거나 늦은 성공 응답이 와도 종결된 시도가 다시 활성화되지 않도록 한다. 확정 전 실패 처리에서도 이미 발생한 예약을 추적할 수 있어야 한다.
- Redis와 신규 DB에 하나의 원자적 전역 트랜잭션이 있다고 가정하지 않는다. 각 저장소의 멱등 명령과 재시도 가능한 보상으로 유효한 최종 상태에 도달한다.

## 5. 창고·로트·재고 모델

물리 테이블명은 구현 단계에서 확정한다. 다음은 필요한 업무 모델이다.

| 모델 | 필요한 식별과 내용 |
|---|---|
| Warehouse | 고유 ID·코드·이름·주소·운영 상태·신규 예약 허용 여부·선택 우선순위 |
| Sku | 판매 상품과의 1:1 연결·공급사/브랜드 참조. 판매자 상품과 직매입 항목은 구분한다. |
| Lot | SKU·로트 식별·사용기한·품질 상태·입고 참조. 사용기한 변경 이력을 남긴다. |
| StockBalance | SKU × 창고 × 로트별 보유·예약·할당·판매불가 수량과 동시성 제어 정보 |
| Reservation / AllocationLine | 주문·주문 품목·창고·요청 수량·로트별 확보 수량·상태·만료 시각·요청 내용 |
| Supplier / PurchaseOrder | 공급사·발주 품목·발주 수량·매입 단가·잔여 입고 수량 |
| InboundReceipt | 실제 도착 수량·정상/불량/검수 중 구분·로트·입고 확정 내용 |
| OutboundOrder / Line | 주문 품목·할당·창고·로트·피킹/포장/출고 수량·취소 결정 |
| TransferOrder / Line | 출발·도착 창고·로트·확보/출발/이동 중/도착 수량 |
| ReturnReceipt | 원 출고·주문 품목·실제 반품 수령·검수 결과·정상/판매불가 복원 |
| StockCount / Adjustment | 실사 기준 시점·측정 수량·차이·작업자·사유·조정 승인 |
| StockLedger | 원인 업무 ID·SKU·창고·로트·각 수량 차원 변화량·작업자·시각·상관 ID |

재고 잔량은 로트 단위로 저장하고 SKU·창고별 수량은 합산 조회한다. 입고 문서·발주 문서는 물리 재고와 구분한다. 발주 예정 수량을 판매 가능한 실제 보유 수량에 더하지 않는다.

### 수량 정의와 불변조건

- onHand: 실제 보유 수량. 예약·할당·판매불가 수량도 포함하며 아직 출고되지 않은 수량이다.
- reserved: 결제 전 주문이 확보한 수량.
- allocated: 결제 후 출고를 위해 확보한 수량. 피킹·포장 중에도 포함한다.
- blocked: 검수 중·불량·기타 사유로 판매할 수 없는 수량. reserved/allocated와 중복 집계하지 않는다.
- 로트의 산술 가용량: onHand - reserved - allocated - blocked.
- 실제 신규 판매 가능량: 사용기한·품질·창고 운영 조건을 통과한 로트의 가용량 합계.
- 각 수량은 음수가 아니며 reserved + allocated + blocked <= onHand다. 수량 계산과 합산의 오버플로도 거부한다.

사용기한이 지난 로트는 배치 실행 여부와 무관하게 신규 예약·출고에서 제외한다. 예약 뒤 사용기한/품질 조건이 바뀌면 할당·출고 전에 재검사하고, 다른 유효 로트의 확보 또는 출고 중단·보상으로 처리한다. 만료 로트를 제외하기 위해 기존 예약·할당 수량을 무조건 0으로 지우지 않는다.

### 창고와 로트 선택의 초기 기준

출고 가능한 활성 창고를 설정된 우선순위와 안정적인 ID 순으로 조회한다. 요청 품목의 전량을 확보할 수 있는 창고에서만 성공시킨다. 한 창고 안에서는 사용기한이 가까운 유효 로트를 우선하는 FEFO를 적용하고 같은 사용기한은 안정적인 로트 ID로 정렬한다. 한 품목을 같은 창고의 여러 로트에서 확보할 수 있다. 창고 간 총량은 충분해도 단일 창고 전량 확보가 불가능하면 현재 정책의 품목 재고 부족으로 명시한다.

조회 결과만으로 성공을 반환하지 않고 실제 잠금·조건부 갱신과 로트별 확보 기록으로 동시 예약을 방어한다. 거리·배송비·창고 부하 기반 최적화는 후속 범위다.

## 6. 입고·출고·취소·반품·이동

### 입고와 원가

공급사 등록 → 수동 발주 → 도착·검수 → 정상/불량/검수 중 구분 → 입고 확정으로 진행한다. 발주 100개 중 실제 도착 95개 같은 분할 입고를 지원한다. 같은 입고 확정 재전송은 수량·원가 기록을 늘리지 않는다. 남은 발주량과 초과 입고 정책은 S2 계약에서 명시하고, 기본은 승인되지 않은 초과 입고 거부다.

입고 확정 시 매입 단가·금액과 발주 참조를 보존한다. 공급사 매입금액 관리와 입점 판매대금 정산은 별개다. 은행·외부 회계 시스템 지급 실행, 세무·원가 회계 체계 전체는 초기 범위에 넣지 않는다.

### 출고와 배송

예약 → 결제 확인 후 할당 → 출고 지시 → 피킹 → 검수·포장 → 실제 출고 확정 → 배송 시작 → 배송 완료로 진행한다. 결제만으로 onHand를 차감하지 않는다. 출고 확정 시 onHand와 allocated를 함께 차감하고 출고·원장·Outbox를 기록한다.

플랫폼 SellerOrder 하나에 창고별 OutboundOrder·Shipment가 여러 개 연결될 수 있다. 기존 shipping의 seller_order_id UNIQUE를 모든 직매입 배송에 그대로 적용하지 않는다. 출고 지시 ID를 기준으로 중복 배송 생성을 막는다. 기존 입점 배송 정책은 유지하며 직매입은 기존 자동 출고 스케줄러가 창고 작업을 건너뛰지 못하게 한다.

### 취소와 반품

직매입은 주문 품목 전량을 취소 단위로 사용한다. 피킹 전에는 동일 예약/할당과 출고 지시의 경쟁을 보호한 뒤 해제한다. 피킹 시작 후에는 창고 확인 대기·승인·거절을 기록하고 승인 전에 환불·가용 재고 복원을 확정하지 않는다. 부분 피킹된 물건의 원위치 복귀도 확인한다. 출고 확정 후에는 단순 취소를 거부하고 반품으로 연결한다.

반품은 수령·검수 후에만 재고를 복원하며 정상 수량과 판매불가 수량을 구분한다. 고객 환불 성공만으로 실물 재고를 증가시키지 않는다. 최소 반품 접수·수령·검수·복원 API는 S6에 포함하고 수거사 연동·교환은 후속 범위다.

현재 PaymentRefund의 (payment_id, seller_order_id) UNIQUE와 판매자 단위 환불은 직매입 여러 품목의 독립 취소를 표현하지 못한다. S5에서 판매 방식·원 주문 품목·취소/환불 요청을 식별하는 계약과 제약을 설계하고, 기존 입점 중복 방어·총환불 한도·정산 receipt를 보존한다. 식별자만 바꾸어 중복 환불을 허용하지 않는다.

### 창고 이동과 실사

이동 요청 → 출발 창고 수량 확보 → 이동 출고 → 이동 중 → 도착 입고로 진행한다. 요청 단계부터 고객 예약과 경쟁을 보호한다. 출발 이후 도착 전에는 어느 창고에서도 판매하지 않으며 출발 보유 + 도착 보유 + 이동 중 수량으로 보존을 검증한다. 부분 도착·미도착과 중복 확정을 기록하고 출발 후 취소를 가용량 단순 복원으로 처리하지 않는다.

실사는 기준 시점과 진행 중 예약·출고·이동을 고려한 조정 문서로 처리한다. 현재 수량을 무조건 실사 숫자로 덮어쓰지 않는다. S8에서 실사 중 작업 차단 또는 기준 이후 변동 반영 방식 중 실제 요구에 맞는 최소 방법을 확정한다.

## 7. 결제·정산과 복구 경계

한 고객 결제에는 입점과 직매입 금액이 함께 들어갈 수 있다. 입점에는 기존 판매자 정산·수수료를 적용하고 직매입은 자기 자신에게 지급할 판매자 정산을 생성하지 않는다. 직매입 환불도 입점 settlement를 조회·차감하지 않도록 이벤트/소비자를 구분한다.

결제 후 직매입 할당을 요청할 때도 주문 DB 잠금을 보유한 채 원격 호출하지 않는다. 처리 상태를 기록하고 결과를 조건부 반영한다. 확정 실패가 일시적이면 같은 요청으로 복구하고, 만료 등 종결 실패면 해당 품목을 취소·환불하는 보상을 진행한다. 다른 확정 품목은 유지하며 보상 중 품목은 출고할 수 없다. 이미 취소된 품목에 늦은 할당 결과가 와도 주문을 되살리지 않는다.

## 8. 권한·이력·운영

입점 판매자는 자기 입점 상품 재고만 수정한다. 공식 판매 주체·창고·공급사 설정과 직매입 입출고는 플랫폼 관리자와 허용된 창고 작업자가 처리한다. 공급사는 납품한 플랫폼 소유 재고를 임의로 수정할 수 없다. 수량 조정·검수·입출고에는 작업자·사유·원 업무 문서가 남아야 한다.

재고 서비스의 내부 예약 API와 관리자 작업 API는 서버 간 인증 및 사용자/창고 권한 검사를 둔다. Gateway 경유 여부에만 의존하지 않는다. S1에서 구체적인 인증 계약을 확정하며 실제 자격 증명을 문서·테스트 결과에 기록하지 않는다.

API·Swagger로 먼저 운영하고 S8에서 창고/로트 재고 조회, 입고·출고 작업, 이동·실사·실패 복구 상태를 확인하는 최소 관리자 화면을 추가한다. 고객 스토어 전체 프런트엔드 개편은 별도 범위다.

## 9. 대표 로컬 통합 플로우 — S6 필수 완료 조건

신규 inventory-service까지 포함한 최신 로컬 실행 구성에서 실제 PostgreSQL·Redis·Kafka와 서비스 간 API/Outbox를 사용한다. UI·실제 PG·택배사·실물 창고 없이 관리자 API와 기존 보호된 결제 시뮬레이션으로 재현한다. MockMvc·mock 기반 검증만으로 전체 플로우 통과를 보고하지 않는다.

### 준비 데이터와 수량

각 실행에 고유 runId를 붙여 테스트 전용 공급사·상품·사용자·발주·로트·창고 데이터를 식별한다. 만료/유효 로트는 테스트 기준 시각으로 생성하며 OS 시간을 변경하지 않는다.

| 판매 주체 | 상품 | 재고 경로/위치 | 초기 판매 가능 수량 | 요청 | 기대 |
|---|---|---|---:|---:|---|
| 입점 판매자 A | 클렌저 | 기존 판매자 Redis 경로 | 10 | 1 | 성공 |
| 플랫폼 | 샴푸 | 중앙창고의 유효 로트 | 100 | 2 | 성공 |
| 플랫폼 | 크림 | 도심창고의 유효 로트 | 20 | 1 | 성공 |
| 플랫폼 | 마스크팩 | 중앙창고 | 0 | 1 | 품절 제외 |

샴푸·크림은 공급사·수동 발주·검수·실제 입고 확정 API를 통해 준비한다. 수량을 DB에 직접 넣어 입고 검증을 생략하지 않는다. 유효 로트와 별개인 만료 로트를 추가하고 예약·출고에 사용되지 않는지 확인한다.

### 단계별 관측과 기대 결과

1. 네 품목을 혼합 주문한다. 입점/직매입이 각각 올바른 재고 경로를 사용한다. 성공 3품목·실패 1품목이며 실패 마스크팩은 주문·청구 금액에 포함되지 않는다.
2. 직매입 onHand는 샴푸 100·크림 20인 채 reserved가 2·1, 가용량이 98·19가 된다. 입점 Redis 가용량은 9다. 주문 시점의 기존 입점 DB 투영은 현행 비동기 계약에 따라 확인한다.
3. 성공 구성·최종 금액·직매입 배송비 1회 계산을 고객 API로 확인한 뒤 결제를 시작한다. 배송비 숫자는 테스트 입력이며 확정된 사업 요율이 아니다.
4. 기본 차단된 실제 PG 경로를 열지 않고 /api/payments/simulation/webhook을 명시적 payment-simulation 프로필·전용 토큰·access JWT로 호출한다. 실제 /payments/webhook의 미구성 503과 prod 차단 정책은 유지한다.
5. 결제 후 직매입 reserved는 0, allocated는 2·1, onHand는 여전히 100·20이다. 플랫폼 판매자 묶음 하나에 창고별 출고 지시 2건이 연결된다. 입점 상품은 기존 확정·배송 경로로 진행한다.
6. 관리자 API로 각 출고 지시의 피킹·검수·포장·출고를 수행한다. 직매입 onHand는 샴푸 98·크림 19, reserved/allocated는 0이다. 재전송은 수량·배송 건수를 늘리지 않는다.
7. 배송 완료를 처리하고 입점 가용/최종 동기화 수량 9, 직매입 잔량·로트·원장·출고·배송 관계를 확인한다. 입점 정산만 생성되고 직매입에는 판매자 수수료 정산·자기 지급 건이 생기지 않는다.

금액 예시용 fixture를 쓰면 클렌저 12,000원, 샴푸 10,000원×2, 크림 15,000원, 직매입 배송비 3,000원, 입점 배송비 0원으로 총 50,000원을 기대할 수 있다. 이 숫자는 테스트 입력일 뿐 운영 가격·배송비 확정값이 아니다. 실제 시나리오는 fixture/서버 정책으로 기대 금액을 계산한다.

### 실행·증거·추가 분기

S6에서 명령 하나로 실행할 통합 시나리오 스크립트와 사전 준비 방법을 제공한다. 기존 image:latest에 새 코드가 있다고 가정하지 않고 테스트할 소스로 빌드한 서비스를 사용한다. 이벤트 완료는 고정 sleep 성공 가정 대신 제한 시간 내 상태를 조회해 판정한다. runId·요청/예약/문서 ID·민감정보를 제거한 응답·기대/실제 수량·검증 결과를 저장하고 실패 단계에서 명확히 종료한다. 정리는 해당 실행 데이터만 대상으로 하며 공유 DB 초기화를 전제하지 않는다.

- 결제 실패·예약 만료: 예약 해제 및 중복 해제 방지.
- 같은 입고·예약·출고 재전송: 한 번의 효과와 요청 내용 충돌 거부.
- 성공 응답 유실·해제 실패: 같은 ID 조회·재시도·서비스 재시작 후 영속 상태 복구.
- 마지막 유효 재고의 동시 구매: 초과 예약 방지.
- 결제/예약 만료 및 취소/피킹/출고 경합: 종결 상태 보존과 실제 출고된 재고의 오복원 방지.
- 같은 플랫폼 주문의 서로 다른 품목 취소: 독립 환불, 총환불 한도, 잔존 품목·출고·배송비 보존.
- 출고 후 반품: 실제 수령 전 미복원, 정상/불량 검수 결과에 따른 복원.
- S7 이동·S8 실사 완료 후에는 해당 시나리오를 추가한다. S6 기본 플로우를 S8까지 미루지 않는다.

이 시나리오와 테스트는 앞으로 구현할 완료 조건이다. 작성 시점에 신규 서비스나 위 통합 테스트가 존재하거나 통과했다고 기록하지 않는다.

## 10. 구현 단계에서 구체화할 항목

S1에서 이벤트 버전/필드, 공식 판매 주체 발급, 내부·관리자 인증, 주문 확인 API·금액 버전, 스키마 이름을 확정한다. S3에서 예약 유효시간·사용기한 경계·타임아웃/재시도 상한을 정한다. S5에서 배송비 환불 배분·품목 환불 계약을, S6에서 창고 취소 확인 API와 배송 관계를, S8에서 실사 경합 정책·관리자 화면 구성을 확정한다. 위 합의를 바꾸지 않는 구현 세부는 기존 규칙과 실제 검증으로 선택하고 결과를 남긴다.
