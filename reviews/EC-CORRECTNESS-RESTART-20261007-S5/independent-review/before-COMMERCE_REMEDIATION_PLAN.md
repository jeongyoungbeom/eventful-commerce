## 1단계 — 환불을 정산에 한 번만 반영

**문제:** 같은 `refundId`가 다른 `eventId`로 다시 발행되면 정산에서 다시 차감된다.

**변경:** 환불 ID 기준 처리 기록과 DB UNIQUE 제약을 마련한다. 처리 기록 저장과 정산 금액 갱신을 같은 로컬 트랜잭션에 묶는다. 같은 정산에 대한 동시 환불을 보호하고 환불 한도를 검사한다. 동일 ID에 다른 내용이 들어오는 경우를 정상 중복과 구분한다. 구체적인 테이블·락 선택은 현재 코드에 맞는 최소 구현으로 결정한다.

**완료 조건과 검증:** 같은 eventId 재전달, 같은 refundId의 다른 eventId 재발행, 동일 환불 동시 처리, 서로 다른 환불의 동시 처리, 정상 신규 환불, 잘못된 금액·내용을 검증한다. 실제 PostgreSQL과 Spring 트랜잭션에서 처리 기록·금액 동반 롤백과 UNIQUE 동작을 확인한다. 정산·결제의 직접 영향받는 테스트를 통과시키고 독립 리뷰를 마친다.

## 2단계 — 결제 경합과 대기 취소 유실 방지

**문제:** 웹훅·취소·대사가 같은 결제를 동시에 수정할 수 있다. 결제 전 판매자 A·B를 취소하면 마지막 payload만 남는다.

**변경:** Payment를 변경하는 모든 경로에 일관된 동시성 제어를 적용한다. 취소 대기는 판매자 주문별로 누적 보존하고, 성공 결제 후 각각 한 번만 환불한다. 기존 DB 자료의 이전·legacy JSON 호환 처리는 요구하지 않는다.

**완료 조건과 검증:** 동시 성공/실패 웹훅의 단일 종결 결과, 성공 중복, A→B/B→A 취소, 웹훅·취소·대사 경합, 중복 취소, 환불 한도와 롤백을 실제 PostgreSQL·Spring Data 저장소·트랜잭션 프록시로 검증한다. 독립 리뷰를 마친다.

## 3단계 — 부분 취소와 예약 만료 수정

**문제:** 결제 전 일부 판매자 주문을 취소하면 나머지 예약 주문이 확정되지 않는다. 만료 후보 조회 뒤 확정된 주문도 일반 취소 경로에서 취소될 수 있다.

**변경:** 살아 있는 RESERVED 판매자 주문만 확정하고 취소된 항목은 확정·배송 이벤트에서 제외한다. 만료 처리 트랜잭션에서 현재 상태와 expiresAt을 다시 확인하고 확정과의 경합을 보호한다.

**완료 조건과 검증:** 결제 전 일부 취소, 결제 후 일부 취소, 만료 조회→결제 확정, 만료→늦은 결제, 확정/만료 동시 처리, 전부 취소→늦은 결제와 중복 이벤트를 검증한다. 취소 항목 재확정과 확정 항목 만료 취소가 없어야 한다. 변경된 이벤트의 실제 caller도 필요한 범위에서 검증하고 독립 리뷰를 마친다.

## 4단계 — 배송과 취소·환불 연결

**문제:** 배송이 시작되거나 완료된 주문도 단순 취소·환불·판매 재고 복원이 진행될 수 있다.

**변경:** 배송 준비 중 취소와 출고 후 취소 거절의 경계를 정한다. 취소 가능 여부가 결정되기 전에 환불·판매 재고 복원을 확정하지 않는다. 취소가 먼저 도착하고 주문 확정이 늦게 도착해도 배송을 만들지 않도록 처리한다. 반품 수령·검수 기능은 이번 범위에 추가하지 않는다.

**완료 조건과 검증:** 준비 중 취소, 배송 시작과 취소 경합, 출고/완료 후 취소 거절, 이벤트 순서 역전·중복, 재기동 후 보류 복구를 검증한다. 배송이 계속되는 주문에는 단순 환불·재고 복원이 없어야 하고 API에서 대기와 거절을 구분해야 한다. 독립 리뷰를 마친다.

## 5단계 — 정산 배치 누락 방지

**문제:** 처리 중 PENDING 집합은 줄어드는데 페이지 OFFSET은 증가해서 다음 대상을 건너뛴다.

**변경:** 키 기반 조회, 실행별 대상 고정 등 재시작 요구를 만족하는 최소 방식을 선택한다. 조회 순서를 ID까지 포함해 안정적으로 정하고 환불 갱신을 덮어쓰지 않게 한다.

**완료 조건과 검증:** 대상 0/1/999/1000/1001/2000건, 기간 경계, 중간 실패·재시작, 동일 작업 재실행, 배치 확정·환불 경합을 실제 DB에서 검증한다. 2000건을 모두 처리하고 누락·중복 효과·금액 덮어쓰기가 없어야 한다. 독립 리뷰를 마친다.

## 6단계 — 웹훅 검증 경계 보완

**문제:** 결제와 다른 금액의 웹훅이나 검증되지 않은 요청으로 결제를 확정할 수 있다. 허용하지 않은 결과 값도 결제 실패로 반영된다.

**변경:** 금액·거래 ID·허용 결과·발신자 검증 계약을 명확히 한다. 실제 PG와 로컬 시뮬레이션을 구분하고, PG 검증자가 구성되지 않은 실제 수신 경로는 기본 차단한다. 보호된 로컬 테스트 경로가 필요한 경우 기존 프로젝트 테스트와 함께 맞춘다. 임의 서명 규격을 실제 PG 인증이라고 구현하지 않는다.

**완료 조건과 검증:** 금액 불일치·누락, 거래 ID 불일치·재사용, 미허용 result, 인증 없는 요청, 잘못된 인증·검증자 미설정, 기본 프로필의 시뮬레이션 비활성, 보호된 로컬 테스트의 정상 흐름을 검증한다. gateway와 서비스 진입점을 모두 확인하고 독립 리뷰를 마친다. ARL 하네스 복원이나 실제 PG 호출은 요구하지 않는다.

## 유지할 설계 조건

- ARL 하네스·실험 코드·전용 모듈·문서는 복원하지 않는다.
- 로컬 DB는 새로 초기화할 수 있다는 사용자 요구를 따른다. 과거 데이터 이전, 기존 환불 receipt 채우기, 적용 이력 보존과 호환 분기는 추가하지 않는다. 새 스키마의 정합성 제약과 필요한 스키마 정의는 유지한다.
- 이 조건은 로컬 개발 대상에 한정한다. prod 운영 정책을 바꾸는 결정이 아니며 이번 문서 갱신에서 DB를 초기화하지 않았다.
- 기존 인증·멱등성·트랜잭션·보상·재고 처리를 불필요한 코드로 간주해 제거하지 않는다. 새 창고·물류·반품 도메인 확장은 1~6단계 이후 별도 작업으로 다룬다.
